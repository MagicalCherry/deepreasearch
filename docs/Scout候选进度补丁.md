# v2.3.3：候选进度保存

1038单题诊断显示团队成员已被读到，但补搜没有持续保存逐候选核查状态。用户授权先修复进度保存。学员首次专项原始输出为收集阶段1 error in 0.13s；未提供完整异常栈，不声称已核实具体异常类型。

新增candidate_progress纯模块，按规范化候选名保存checked、pending、next_query及每轮history。原始报告独立追加Candidate Progress JSON块，进入旧引用纠错/事实解析前隔离，避免JSON被当成候选名或事实。每条支持/反驳状态的docid须来自该Scout实际观察文档；否则降为unresolved。这里只核对来源可用性，不证明语义真实，候选始终是hypothesis，不自动进入Facts。

候选报告完成时保存到state._candidate_progress，并同步Scout候选视图；后续初始任务或补搜的payload单独携带完整进度。新报告None或无进度不清空旧记录，同条件新观察更新当前视图并保留旧history。Writer/Critic重试回滚不清除此进度。提示词要求分别检查具体候选与一个缺失条件，不把多人混搜、不因角色是负责人就认定为目标；这是一项模型行为要求，尚未增加程序强制候选调度。

局限：本补丁在每个子任务报告结束时落盘到运行state与trace事件，不在每一次工具调用后重新抽取；没有从旧日志自动生成候选，也不保证模型一定填出所有名字。原报告若未输出合法JSON，进度不更新，旧进度保留；需从candidate_progress事件的update_count观察。没有让Critic读取或改写候选进度，没有把历史金标植入运行策略，没有额外增加模型调用。模型、600秒、搜索/阅读/工具预算不变。

v2.3.3仅新增candidate_progress=True，旧版不启用新提示词和解析。未执行测试或付费请求，等待学员手动验证专项及全量。
