# 项目理解

## 项目背景与用户痛点

项目源于本科课题研究中的行业调研需求：为了了解某个研究方向的技术进展及产业应用，需要反复查阅论文、企业官网、产品公告和行业新闻，再整理成行业信息报告。以毫米波技术、半导体行业为例，用户既需要梳理近三个月的技术进展，也需要持续跟踪近一周的重要新闻和新技术信息。

人工完成这类任务，主要面临以下问题：

1. **资料分散，检索与整理耗时。** 同一主题的信息分布在多个网站，用户需要反复搜索、打开原文、去除重复报道，再按技术方向、企业或应用场景组织内容。
2. **时效和统计口径难以核实。** 发布日期、事件发生日期、产品代际及参数条件可能不同，旧资料或不同条件下的数据容易被误写成最新行业结论。
3. **只有零散线索，难以定位研究对象。** 用户可能只记得某家企业的合作经历、产品发布的大致年份、频段或工艺等特征，却不知道准确名称。单次关键词搜索往往只能得到部分相关的候选，需要多轮检索并逐项核对，才能找到目标企业、产品或技术。
4. **找到对象后，仍难以取得有出处的准确数据。** 定位企业或产品只是中间步骤，报告真正需要的可能是某项性能参数、技术指标或统计结果。用户还需继续寻找原始资料，核对单位、测试条件和适用范围，防止把相似对象的数据或缺乏证据的推断写进报告。

例如，用户可能提出以下调研需求（场景示例，并非已经验证的真实产品案例）：

> 我记得某企业在一段时间内推出过一款用于汽车雷达的毫米波芯片，支持特定频段、采用某种工艺，并与一家车企有合作。请根据这些线索定位产品，核实它的关键技术参数，并将技术特点及出处整理进近三个月的行业研究报告。

这个痛点与S03手搜练习的检索过程一致：先将时间、经历、属性等线索拆成条件，搜索候选并交叉核对；确定对象后，再查找题目真正要求的统计指标。练习说明了行业报告中“对象定位—事实核查—数据取证”的需求，不能以仅找到对象名称代替完成用户任务。此处不记录该评测题的答案或证据标注。

因此，项目定位为**面向行业动态追踪与专题调研的行业信息研究报告助手**：用户指定行业、时间范围和关注主题后，系统检索与阅读资料、核查关键事实，归纳技术进展和产业事件，形成附来源引用的专题报告或行业周报。多跳检索问答是支撑报告事实准确性的底层能力。

### 产品愿景与当前开发边界

行业报告是应用场景与产品目标；当前课程主线是在固定网页语料和BM25检索服务上，评测与改进复杂问题的搜索、阅读和作答能力。真实联网、时间范围过滤、最新行业动态覆盖和报告质量需要分别验证，不能由固定题集成绩直接推断已经实现。

## 要做什么

在已有行业信息助手的基础上，接手并逐步改进深度研究 Agent，让它更善于搜索资料、核对信息并回答需要多步研究的问题。

## 怎么算做完

后端要能接入现有前端，支持研究过程展示、评测运行、题集管理和运行对照等功能，并通过任务书规定的功能验收。

## 怎么算做好

用固定 dev100 开发集评测每个版本，目标是准确率至少 75%、证据召回至少 70%、校准误差不超过 10、运行错误不超过 2 题、平均耗时不超过 300 秒、平均检索次数不超过 50 次。改进要能从运行记录和版本对照中追溯。

## 几条规矩

- 评测答案和证据文档编号只供评测程序使用，不能进入 Agent 的提示词、工具结果或检索请求。
- 检索使用课程指定的固定语料和 BM25 服务，不把语料改成向量检索。
- 每次改进都通过评测数据判断效果，并保存代码版本和运行配置。
- 不读取、打印或提交 `.env` 文件及密钥。
