# 行业信息研究助手与 DeepResearch 评测系统

> 后续状态更新：Qwen3.8 dev100已完成并由用户冻结，80%准确率、80.68%召回、32.97校准误差、0运行错误，平均218.30秒；六指标五项达标，校准未过。新冻结标签final-qwen38，历史final不变。正文保留撰写时的过程记录，其中“后台运行中”是当时状态，现已结束。

## 项目概览

本项目是在已有行业信息助手基础上开发的深度研究与评测系统。它将大语言模型、固定网页语料检索、多Agent协作和可追溯评测结合起来，用于研究需要多次搜索、阅读和交叉验证的问题。

用户输入一个问题后，系统先拆解条件、寻找候选，再检索和阅读资料，形成答案备忘录，经过审核和必要的补充检索，最终输出答案、解释与置信度。同时，它保存研究轨迹、工具调用统计和模型用量，支持查看历史结果、比较版本和复盘错误。

**项目的主要交付是可运行、可观察、可评测的研究系统。**行业调研是产品应用场景；当前已重点实现和验证的是固定语料上的多跳问答研究能力。实时互联网资讯、自动行业周报和完整生产运营能力仍需独立建设与验收。

| 项目项 | 说明 |
|---|---|
| 应用方向 | 行业专题研究、资料查证、多跳事实问答 |
| 当前研究方式 | 固定网页语料上的BM25检索与正文阅读 |
| Agent模式 | 闭卷、单Agent、多Agent及其版本化迭代 |
| 模型接入 | OpenRouter、百炼兼容接口 |
| 当前新增评测模型 | OpenRouter Qwen3.8 Flash |
| 研究主线 | 原v2.3；后续实验补丁保留，但未选作冻结主线 |
| 使用入口 | Web页面、命令行、HTTP API |
| 项目性质 | 课程驱动的研究原型与评测平台，尚未完成全部最终验收 |

## 一、项目背景与目标

### 1.1 为什么需要深度研究

复杂调研往往不是一次搜索就能回答。例如，用户可能通过人物经历、时间范围、地理位置和事件关系描述一个对象，然后要求给出该对象的某项具体统计或作品名称。

这类任务包含多个步骤：

1. 理解问题真正要求的答案类型。
2. 把题面拆成可验证的条件。
3. 根据部分线索找到候选对象。
4. 查证候选是否满足其余条件。
5. 找到回答所需的原始资料。
6. 根据证据给出具体答案，并表达不确定性。

如果模型只依赖记忆，容易产生看似合理的答案；如果只拿搜索摘要，可能错过关键条件；如果多个Agent只是重复搜索，则会增加成本而没有带来证据增量。

本项目围绕这些问题，建立从检索、阅读、证据交接到审核和评测的完整流程。

### 1.2 目标用户

- **研究使用者**：输入问题，查看答案与证据过程。
- **Agent开发者**：调整规划、工具与协作机制，定位质量瓶颈。
- **评测人员**：在固定题集上对照版本，检查质量、成本和稳定性。
- **课程学习者**：通过实际代码、测试和执行轨迹理解多Agent系统。

这些是目标使用角色，不代表系统已完成多租户权限和面向外部客户的商业部署。

## 二、用户能做什么

### 2.1 发起一次研究

用户选择研究版本并输入问题。系统通过服务端事件流返回规划、搜索、阅读、事实、审核及最终结果。页面按角色显示过程，用户可以观察研究方向，也可以停止研究。

研究请求仅接收问题、版本及可选问题编号，不接收标准答案或证据标注。

### 2.2 查看历史研究与评测

历史运行页面提供：

- 运行状态、版本、题集、完成数量和错误数量。
- 准确率、证据召回、校准误差及资源统计。
- 逐题模型答案、标准答案与判分状态。
- 规划、各Scout、报告撰写、审核及最终作答的事件。
- 可追溯的文档编号和文档内容查看入口。

标准答案用于用户离线检查，不进入研究Agent的模型输入。某阶段未保存正文或完整意见时，页面明确显示记录缺失，不能凭空恢复历史内容。

### 2.3 管理题集与执行评测

系统支持内置smoke20、dev100，以及用户上传的自定义题集。页面可发起批量评测并跟踪状态，也提供命令行方式，便于控制模型配置、并发和运行编号。

当前用户实际采用命令行运行、贴回输出的方式，避免误点前端新建评测导致重复费用。页面具备发起入口，不意味着每次查看历史都会触发研究。

### 2.4 对比不同版本

同题对照支持查看两个版本的答案与轨迹；离线比较工具进一步统计：

- 新版本改善的题目。
- 新版本退步的题目。
- 两版都对、两版都错的题目。
- 运行错误的变化。
- 配对准确率差异的McNemar精确检验。

这样可以区分“总分变化很小但具体题目大量翻转”和“同一批题稳定改善”。

## 三、系统总体架构

系统由既有产品外壳、新开发的研究评测后端、检索服务、模型服务及本地运行记录组成。

```text
用户
 ├─ Web前端：React / TypeScript / Ant Design
 │    ├─ 原产品功能 → 产品后端
 │    └─ 研究与评测 → FastAPI评测后端
 └─ 命令行：app.cli
                         │
                         ▼
              Runner + 版本注册表 + Trace
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       闭卷基线       单Agent基线      多Agent工作流
                                        │
                              Chief / Scout / Writer / Critic
                                        │
                    ┌───────────────────┴─────────────────┐
                    ▼                                     ▼
              SearchClient                            LLM适配层
                    │                                     │
              本地BM25服务                      OpenRouter / 百炼
                    │
              固定网页语料
```

图中的产品后端与评测后端职责不同。产品界面的知识库、新闻、数据库等入口来自既有系统外壳，不能由本项目的DeepResearch评测结果推断这些模块均已完成改进或验收。

## 四、多Agent研究流程

### 4.1 Chief：问题规划

Chief读取原问题，提取全部条件和答案类型，拆成研究子任务，并提出初始检索词。

早期原系统偏向行业报告模板，容易生成市场概况、竞争格局等不适合事实问答的大纲。迭代版改为约束驱动规划，要求查询适合英文语料检索。

规划的作用是为后续搜索提供方向，并不等于已经验证条件。Chief提出的候选、实体和假设仍需检索证据支持。

### 4.2 Scout：搜索与阅读

多个Scout围绕不同子问题并行研究。当前主线使用ReAct方式：模型观察已有上下文，自主决定下一次使用搜索、翻页还是读文档，然后继续推理或输出发现报告。

三个工具分别是：

| 工具 | 功能 | 重要区别 |
|---|---|---|
| search | 执行BM25查询，缓存深排结果，展示部分片段和标题 | 会产生实际检索请求 |
| read_search_results | 查看已有搜索结果的指定排名区间 | 从本地缓存翻页，不重新搜索 |
| read_document | 按文档编号和行号读取正文 | 用于补全摘要中没有的证据 |

搜索深排缓存200条，初次显示5条片段及接下来的15条标题。**缓存200条不等于模型读过200条，也不等于200条全部计入可见证据。**正文按行分块，避免一次把整篇长文直接灌入上下文。

Scout提交Findings与Candidates。带合法来源的发现可用于事实交接，候选仍是待验证假设。主线保留一次引用纠错，使用实际文档编号，而不是把列表序号或内部事实编号当成文档编号。

### 4.3 Writer：答案备忘录

Writer接收问题、约束、已收集事实、Scout报告及审核反馈，生成围绕问题的答案备忘录。

备忘录应说明最可能答案、条件验证情况、证据链和缺口。Scout探索报告不是独立证据；报告中的结论不能仅因被写进文字就自动变成事实。

与长篇行业报告相比，备忘录形式更适合多跳问答的事实核查，也便于Critic逐项审核。

### 4.4 Critic：逐约束审核

Critic检查每个条件是否有可用来源支持，并输出：

- 条件状态：verified、refuted或unverified。
- 对应文档编号与解释。
- 总体评分及审核结论。
- 需要修订的问题和需要补搜的查询。

无效、结构不完整的审核不能直接视为通过。证据不足时可以回到Scout补搜，只有写作问题时回到Writer修订。

```text
规划 → Scout研究 → Writer备忘录 → Critic审核
                                  ├─ 通过 → 最终作答
                                  ├─ 缺证据 → 补搜 → 重写 → 再审核
                                  └─ 文字修订 → 重写 → 再审核
```

回环受审核轮数、无新增证据、工具预算和时间预算约束，不会无条件持续到审核通过。

### 4.5 最终作答与置信度

最终抽取步骤从原问题、报告和事实生成三字段答案：

```text
Explanation: 解释与证据
Exact Answer: 具体答案
Confidence: 0–100%
```

v2.3在最后阶段按有效约束审核的验证比例计算：

```text
置信度 = 20 + 75 × 已验证条件数 / 条件总数
```

没有有效审核计数时保留原置信度。该公式是开发集上采用的规则映射，不是已经独立验证的真实正确概率。它可能因为证据交接不足或审核过严而低估实际答案正确率。

## 五、检索与知识来源

### 5.1 固定语料，而非实时互联网

检索服务使用课程提供的固定网页语料，文档级索引约100195篇。每篇文档有稳定编号，Agent通过搜索片段和正文接口获取资料。

当前系统没有把研究主线替换为向量检索，也不以联网搜题作为开发捷径。外部网页最新变化不会自动进入固定语料，因此不能承诺时效性覆盖。

### 5.2 BM25参数选择

主线显式选择文档索引k25b1：

| 参数 | 值 |
|---|---:|
| k1 | 25 |
| b | 1 |
| unit | doc |
| snippet | passage，查询相关片段 |

选择依据是历史真实查询的离线回放，而非只凭经验。与默认索引相比，k25b1在该批查询中表现出更高召回。查询相关片段帮助模型观察包含检索词的内容，但不保证每次都截出最终答案。

段落索引psg曾构建并回放，当前配置收益不足且资源成本高，因此没有作为主线。该结论只针对已测参数，不代表所有段落检索方案无效。

## 六、模型接入与配置

### 6.1 统一模型适配

模型层采用异步兼容接口，负责组织消息、限制输出、关闭思考、累计token及处理错误。支持通过平台和模型配置切换OpenRouter或百炼。

各Agent共享同一次研究的异步模型适配实例，但通过不同Prompt、上下文和角色职责调用；不是必须给每个角色配置不同模型。

当前用户已切换OpenRouter Qwen3.8 Flash，配置检查输出为：

```text
openrouter qwen/qwen3.8-flash 131072
```

131072是配置层模型输出上限；部分角色调用仍显式指定16000等较低上限，最终请求取角色参数与模型上限中的较小值。因此不能把配置上限理解为所有请求均使用131072。

### 6.2 配置与标注隔离

- 模型凭证保存在本地独立配置中，不进入仓库和运行快照。
- 平台、模型、输出限制和检索地址可通过配置选择。
- 研究输入只保留query_id和query。
- answer、gold_docids、evidence_docids供离线评测与诊断使用，不作为研究线索注入。
- 正常检索得到的文档编号可被模型引用；禁止的是从标注字段泄露编号，而不是禁止所有编号出现。

## 七、预算、并发与异常处理

### 7.1 时间控制

当前主线总预算600秒，最终作答预留60秒。使用单调时钟计时，避免系统时间调整影响耗时计算。

| 截止点 | 默认时刻 | 行为 |
|---|---:|---|
| 软截止 | 420秒 | 停止开启新的研究工具或审核 |
| 研究硬截止 | 540秒 | 取消研究阶段，转入最终作答 |
| 总截止 | 600秒 | 停止继续请求，给出明确的预算结束结果 |

预算的目的包括控制研究长尾和避免无限循环，不等于实现美元总费用上限，也不能由一次测试证明所有网络故障下都有毫秒级截止保证。

### 7.2 工具预算

当前主线有整题最多50次实际搜索、8篇唯一阅读文档，以及每子任务最多12次工具调用等限制。

阅读调用次数可以高于8，因为同一篇文档可能分块读取多次；不能把“读取块数”“去重篇数”和“搜索次数”混为同一指标。

### 7.3 批量并发

当前手动评测通常使用并发8，即允许最多8道题同时研究。题内还有多个Scout子任务，因此实际模型请求并行情况不只由题目并发数决定。

提高并发主要影响整批吞吐、连接数、限流及本地检索压力；不保证单题变快或成本下降。运行配置保存实际并发，用于后续比较。

### 7.4 错误与取消

模型错误分为欠费、内容审核、超时及其他服务错误。欠费不继续盲目重试；批量运行触发停止，取消在途和等待任务，保留已成功结果及原始异常。

用户停止实时研究或连接断开时，后端传播取消并清理协程；本地停止并不保证已经发送到云端的请求完全没有计费。

重试和错误记录与最终结果分开看：最后100题错误为0，不等于全过程没有失败尝试，也不等于没有额外费用。

## 八、可观察性与数据保存

### 8.1 事件追踪

每次研究创建独立Trace，记录角色、单调时间和事件内容。当前事件包括：

`agent_start`、`plan`、`search`、`read`、`fact`、`verify`、`answer`、`done`、`error`、`stage_output`。

事件既进入本地记录，也广播到订阅队列，供命令行或SSE页面消费。前端用同一批事件显示角色泳道，离线诊断再按题回放。

这使系统能够回答“查询是否执行”“哪些文档只出现过标题”“实际读了哪篇”“审核指出什么”“最终为何停止”等问题。历史版本未保存的字段不能通过前端修改自动补回。

### 8.2 文件持久化

研究评测记录主要保存在本地runs目录，采用JSON和JSONL，方便追加、排查和恢复。

| 文件 | 内容 |
|---|---|
| config.json | 版本、模型、提交、选项、题面哈希及索引快照 |
| status.json | 当前运行状态、完成数、错误数及PID |
| results.jsonl | 每题答案、事件、耗时、token及错误 |
| judged.jsonl | 与答案对应的判分记录 |
| summary.json | 准确率、召回、校准及资源均值 |
| 来源与续跑记录 | 复用来源、兼容性检查和历史身份 |

原产品容器还依赖PostgreSQL和Redis，但不能把它们说成本次评测JSONL记录的实际存储后端。

### 8.3 续跑与复用

同一运行编号会读取已有成功结果，跳过成功题，只补缺失或错误题。运行配置和源码身份不一致时拒绝续跑，避免把不同系统混成同一实验。

smoke20扩展到dev100时，会校验重叠题面、模型、判分、版本选项、依赖及索引，保留原20题的结果和来源。不同模型之间不直接复用研究答案。

## 九、评测体系与已观察效果

### 9.1 三层验证

| 验证层 | 验证对象 | 方式 |
|---|---|---|
| 代码行为 | 预算、取消、解析、状态、配置、标注隔离等 | pytest、假模型、假检索、临时文件和假时钟 |
| 模型研究质量 | 正确率、证据召回、置信度及耗时 | 真实smoke20/dev100研究和判分 |

最近完成的全量离线测试为355项通过。离线测试通过不等于真实模型研究质量达标。

### 11.3 自定义题集

支持DATASET_DIR指定外部题集目录，研究与OpenRouter判分共用同一解析方式。自定义题集使用合法名称定位JSONL文件，目录相对路径以Projects为基准，文件缺失时报错，不偷偷回退到另一份数据。

上传与删除仍限制在原上传目录，不因DATASET_DIR而改写外部验收数据。外部题集不会自动出现在前端列表，详细边界见`docs/题集目录配置.md`。

## 十二、项目特点

1. **完整研究链条**：从问题规划到证据阅读、审核补搜和最终作答，而不是单次模型问答。
2. **过程可观察**：可以查看角色行为、查询、文档、审核和停止原因，支持定位失败环节。
3. **工具可控**：查询、翻页和正文读取职责明确，有工具、时间与并发限制。
4. **实验可追溯**：每组运行保存模型、配置、索引、源码身份与原始结果，避免只保存一个总分。
5. **基线可对照**：保留闭卷、单Agent和多Agent，避免仅凭架构复杂程度判断效果。
6. **开发与标注隔离**：标准答案用于评测和离线复盘，研究时不从标注字段获取线索。
7. **成本意识明确**：先小样本、复用结果、只续跑失败题，优先离线诊断，但不声称已经实现美元硬预算。

## 十三、现有边界与后续方向

### 已知边界

- 研究依赖固定语料，不保证最新互联网覆盖。
- Scout仍可能被未经验证的候选带偏，或者命中线索后没有读正文。
- Critic可能过严或缺少可靠事实交接，导致正确答案被赋予偏低置信度。
- 最终抽取存在证据不足仍强猜具体答案的已知风险。
- 多次研究和共享开发集调参存在波动与过拟合风险。
- 没有美元总费用强制上限，失败重试和判分可能额外计费。
- 部分早期版本缺完整dev100，不满足每版都完成100题的原始交付要求。
- 运行原始文件保留本地，GitHub只发布代码、文档及运行文件清单，尚未完成验收方交接。
- 部署以本地实验为主，当前材料不能证明已经具备生产级权限隔离、扩缩容、监控和灾备能力。

### 后续可验证的方向

1. 先完成当前Qwen3.8 dev100，确认六项指标与逐题时间表现。
2. 对“命中但未读”和候选方向漂移做分层诊断，避免继续堆叠通用Prompt。
3. 分离答案正确性与证据审核完成度，使用独立数据检验置信度规则。
4. 若新增行为补丁，冻结旧版，以独立版本和对照数据证明收益。
5. 完善运行证据交接与独立部署，再由验收方执行一次730题样本外评测，只返回汇总。

上述是后续方向，不表示已授权自动开发、重新评测或产生费用。

## 总结

本系统将深度研究Agent与评测平台放在同一套工程闭环中：Agent负责寻找和核查证据，工具约束执行边界，Trace记录过程，评测与版本管理检验改动是否有效。

它的价值既在于回答复杂问题，也在于让开发者能够解释“为什么答对、为什么答错、证据在哪一步丢失、改动是否真的有帮助”。当前已经形成可运行的研究原型和较完整的开发评测工具，但整体质量验收与样本外验证仍未完成。
