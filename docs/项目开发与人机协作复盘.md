## 一、我们在做什么

项目场景是行业信息研究助手：通过资料检索、阅读、事实核对和研究报告支持行业调研。课程当前实际训练的是固定网页语料上的多跳问答能力，而不是已经上线的实时行业资讯系统。

我们接手既有前端和多Agent系统，先建立可运行、可观察、可评测的基础，再逐步优化研究流程。研究对象既包括代码，也包括提示词、工具协议、角色分工、证据交接和运行约束。

核心任务有五类：

1. **接通系统**：固定语料BM25服务、模型接口、评测后端、既有产品前端。
2. **建立对照**：闭卷、单Agent、原样多Agent，在明确模型配置下保存基线。
3. **改进研究**：从约束规划、查询扩写、正文阅读，一直迭代到搜/翻/读工具和预算机制。
4. **建立证据**：逐题轨迹、版本比较、错误分类、复用与续跑、置信度与波动分析。
5. **准备交付**：启动说明、版本报告、标注隔离审计、前端复现、Git标签及验收自查。

### 当前验收要求

| 维度 | 要求 |
|---|---|
| 准确率 | dev100 ≥75% |
| 证据召回 | dev100 ≥70% |
| 校准误差 | dev100 ≤10 |
| 运行错误 | dev100 ≤2题 |
| 平均耗时 | ≤300秒/题 |
| 平均实际搜索 | ≤50次/题 |
| 逐题时间 | ≤600秒 |
| 功能 | 健康检查、前端、事件、取消、格式、预算、标注隔离、续跑、错误处理、版本对照、样本外验收 |

课程指定研究和判分使用Qwen3.8 Flash。此前因费用转用Qwen3.7，因此旧结果必须标明模型偏差；切换模型后不能直接复用旧模型答案作为新模型成绩。

## 三、我们怎么开发

### 基本节奏：先暴露问题，再实现，再验证

典型过程是：

1. 从tutor MCP取得当前阶段任务、验收要求和证据格式。
2. 列清本阶段任务、产出、验证方式和费用边界。
3. 先写表达目标行为的测试，让缺失功能以失败形式出现。
4. 用户运行测试并贴回原始输出。
5. 助手根据失败实现代码，避免同时混入多个无关改动。
6. 用户执行专项测试，通过后继续全量pytest。
7. 运行smoke20，判分和复盘后决定是否扩展dev100。
8. 保存版本报告、原始运行、采用理由、提交与标签。

许多阶段出现的“未知版本v1.x”是因为测试先要求该版本存在、注册实现尚未完成。这是测试先行过程中的预期红灯；同时，真实报错也会揭示意外缺陷，不能把所有失败都解释成故意设计。

### 版本门控与实验隔离

`app/versions.py`保存稳定编号、入口与options。新版本复制指定基线选项，再增加本阶段改动，避免直接覆盖旧编号。

需要注意基线并非永远是上一个编号：v2.0基于v1.9做片段实验；v2.1按用户确认回到v1.9.1保留引用修复。因此，版本对比必须检查真实options，不能仅凭编号说是单因素消融。

用户曾授权一边后台补S08，一边开发S10。为防止新代码污染旧批次，使用独立工作树固定S08源码，主工作目录继续迭代。原运行身份及来源保持可追溯。

### 控制变更范围

- 保持课程材料只读，修改自己的项目和运行副本。
- 新文件写用途说明，代码、诊断和交付文档分开。
- 不读取、打印或提交密钥。
- 未明确的问题先讨论选项，等待用户确定方向。
- Prompt和Agent行为变化也作为实验改动记录，不只记录Python函数。
- 修复阶段优先验证具体缺陷，效果评测保持独立身份。

## 四、我们怎么跟进问题

### 从汇总成绩追到执行记录

我们逐步从“准确率很低”转向检查证据链：

| 层次 | 检查的问题 |
|---|---|
| 题面与最终回答类型 | 问的是演员、节目、品种，还是比赛统计？是否答非所问？ |
| Chief规划 | 是否保留全部条件？是否引入题目没有的实体或行业模板？ |
| Scout查询 | 查询是否英文、能否执行、有没有空转、重复、被共享预算拒绝？ |
| 搜索结果 | 金标或相关证据是否真正曝光？不能把缓存200条当成已见证据 |
| 正文阅读 | 线索出现后是否打开？看的是哪个文档、哪段正文？ |
| 事实入库与引用 | 来源编号是否合法？事实是否在交接时丢失或被错误过滤？ |
| Writer | 是否使用已验证事实？是否把探索报告误当证据？ |
| Critic与补搜 | 是否给出具体缺口？补搜是否围绕已有候选推进？ |
| 最终抽取 | 是否把Unknown改成无证据强猜？置信度是否有依据？ |

### 实际排查过的典型问题

1. **搜索语言和方向漂移**：用户从截图发现英文题用中文描述性长句搜索，Chief又生成市场、竞争等模板。我们检查实际提示词和查询，而不是简单归因于模型差。
2. **只搜不读**：即使找到相关或标注文档，Scout也可能继续改写查询，未打开正文。召回问题和阅读问题需要分开统计。
3. **引用编号混淆**：把列表序号、事实内部编号与真实文档编号混用，导致引用校验和事实交接失效。
4. **共享去重冲突**：三个Scout任务不同，但查询可能相似；重复查询被拒绝时，后到Scout未必能看到先前结果。随后尝试共享缓存和并发合并。
5. **候选进度丢失**：初次发现候选，补搜却转向别的人。通过持久化候选、区分部分候选、保存旧证据进行实验。
6. **最终答案强猜**：Writer和Critic已指出证据不足，最终抽取仍被要求给具体候选，可能增加无依据答案。
7. **前端缺失内容难以判断**：页面只有原问题时，不能判断角色没执行、日志没保存还是展示没实现。我们增加真实阶段产出和缺失记录提示，避免用空白暗示正常。

诊断时允许离线对照标准答案和证据编号；研究运行时禁止把这些标注注入Prompt、工具结果或查询。这是两个不同边界。

## 五、怎么测试与评测

### 1. 离线自动化测试

pytest验证代码行为，通常用假模型、假检索、临时文件、假时钟和模拟异常，不产生真实模型费用。

覆盖包括：版本选项、Prompt和工具消息构造、状态转移、预算、取消、错误分类、判分字段、续跑、结果复用、引用校验、候选进度、API、数据目录和前端交付文件。

专项与全量使用同一个PowerShell块：

```powershell
uv run python -X utf8 -m pytest -q tests/某专项测试.py
if ($LASTEXITCODE -eq 0) {
    uv run python -X utf8 -m pytest -q
}
```

这是示意，不是让用户复制不存在的文件。实际交互每次给完整、真实路径的命令。

最近用户返回的全量输出为：

```text
355 passed in 2.84s
```

355项通过说明测试覆盖的行为符合断言，不代表研究答案达到75%、线上模型永不出错，或所有功能已完成真实浏览器验收。

### 2. 真实模型评测

先smoke20检查链路、费用与典型质量，再按授权扩展dev100。用户出于成本曾暂时只跑20题，后又要求从v1.6起先20再100；部分补丁明确例外，只完成冒烟。历史缺失不补造成已完成。

smoke20包含在dev100中时：

- 复用同模型、同研究配置的20题原始答案和对应判分。
- 仅新增80题研究及判分。
- 核对源码、依赖、模型、输出上限、索引和题面。
- 保存source_config与provenance，说明来源及复用关系。
- 不把20题与100题当作两次独立验证。

每组dev100保存四类核心文件：

| 文件 | 用途 |
|---|---|
| config.json | 版本、模型、options、提交号、索引及题面哈希 |
| results.jsonl | 答案、事件、工具次数、token、耗时和错误 |
| judged.jsonl | 与当前答案对应的判分结果 |
| summary.json | 汇总质量与资源指标 |

### 3. 续跑与错误统计

欠费或超时不需要整批重跑。保留成功结果，使用同编号续跑失败或缺失题；源码或配置发生变化时先核对，不手改历史快照绕过检查。

“最终错误0”表示最后有效结果没有运行错误，不能抹掉曾经失败的尝试及其费用。S18的300秒组两题持续失败时，用户选择保留错误报验，并要求说明原因，而不是无休止重试。

并发8表示允许同时研究多道题，不等于单题推理速度提高8倍，也不保证费用更低。它可能降低整批等待时间，也会增加连接、限流和本机检索负载。

### 4. 离线检索回放与统计比较

索引实验使用真实历史查询离线回放，不用金标生成查询，不调用模型。这样先判断检索收益，避免每次换索引都付费重跑完整Agent。

版本比较不只看总分，而是逐题配对：改善多少、退步多少、两者都对/都错多少，再用McNemar精确检验辅助判断。还检查相同完整回答是否被判为不同结果。

原v2.3两次dev100是67和66分，但有13题翻转（+6/-7），说明同配置研究轨迹会波动。不能把净增几题直接说成稳定改善；p值不显著也不能证明两个版本等效。多次探索比较还需要考虑多重比较和独立验证。

### 5. 人工页面验证

用户重建前端、查看历史评测，确认答案、标准答案、阶段产出和审核等展示。只浏览历史记录即可检查页面，不需要重复发起付费研究。

前端修改在独立副本中进行；交付时发现副本被Git忽略，便归档Lanes.tsx和RunsPage.tsx，加入应用脚本、原版/归档哈希及离线复现测试。后来又处理Git在Windows上的LF/CRLF转换，避免新克隆时哈希误报。

## 六、人机怎么交互：这次的 vibe coding

这里的vibe coding不是“只说一句需求，AI自动写完就算成功”。实际采用的是自然语言提出目标、AI实现、用户验证、依据证据反复修正的协作方式。

### 分工

| 参与者 | 主要责任 |
|---|---|
| 用户 | 决定目标、预算、路线与取舍；手动执行命令；返回原始输出和截图；指出不合理行为并追问原因 |
| 助手 | 阅读代码和课程要求；定位原因；提出选项；实现代码与文档；提供可复制命令；分析结果和维护版本记录 |
| tutor MCP | 提供课程步骤、证据要求和阶段验收结论；partial不等于通过 |
| 被开发的研究Agent | 实际调用模型与检索工具，完成问题研究；其回答不是开发助手代答 |

### 一轮真实交互通常是这样

```text
用户：Scout为什么没有搜索？
助手：检查轨迹和代码，区分未调用、被拒绝、缓存复用及记录缺失。
用户：确认修复方向。
助手：先补测试，再实现版本门控，给专项+全量命令。
用户：执行并贴回报错或通过输出。
助手：修正实现，确认离线行为，再给smoke20命令。
用户：运行、付费、贴回状态和判分。
助手：比较逐题结果，说明改善、退步、费用和证据边界。
用户：决定保留、撤回、扩展100题或进入下一阶段。
```

用户截图和质疑多次成为有效需求输入：例如“搜的方向完全偏离”“报告撰写为什么是空的”“是不是只找到了演员却没回答节目”“明明搜到了文档为什么没读”。这些反馈把开发重点从增加功能转向提高过程可解释性。

### 交互方式也经过调整

- 初期逐条命令、逐次反馈；用户负责运行，助手负责开发。
- 用户短暂要求“一条龙”，对特定修复授权自动测试和冒烟。
- 随后用户明确恢复手动粘贴命令，后续不把此前自动执行权限继续沿用。
- 用户要求专项失败测试与全量pytest放在同一命令块，减少重复交流。
- 用户要求后台评测与其他工作并行；开发时需要避免改变后台运行的研究源码或配置。
- 方向不明确时给选项等待确认；费用授权、版本主线和课程推进例外均保留记录。

### 有效之处与暴露的问题

有效之处是反馈快、能围绕真实轨迹小步修改，用户也逐渐参与到搜索策略、证据链和统计解释，而非只验收页面。

问题也很明确：阶段多、对话长，容易出现口头结论与源码状态不同步；只看截图难以定位数据是否保存；最新版本不一定更好；“修了机制”不等于“模型会稳定使用机制”；人工复用脚本中的旧默认值也可能悄悄切回旧模型。

我们通过稳定版本编号、配置快照、原始输出、版本报告、门控开关、发布标签和独立诊断文档降低这些风险。它们不是额外装饰，而是让自然语言驱动开发可追溯的必要部分。

## 七、费用如何影响了开发路线

用户自行承担费用、没有报销，因此成本是实际约束。我们做过的调整包括切换低成本模型、先跑20题、复用20题补80题、只续跑失败题，以及优先离线诊断和回放。

用户报告的账户累计金额与单次运行成本分开记录；累计差可能包含其他研究、判分和失败重试，不能随意当作一组100题的独立费用。

当前Qwen3.8 smoke20研究花费$0.92，均价$0.046/题。按相同均价估计新增80题研究约$3.68，判分另计；这是估算，不是账单，也没有美元硬上限。不能假定换更强模型一定同时提高准确率和降低费用。

## 九、复盘结论

1. **Agent开发不仅是改Prompt**：工具可见性、数据交接、状态保存、错误处理与预算都会改变实际行为。
2. **能回答不等于证据链可靠**：正确答案可能来自不完整证据或猜测；应同时看轨迹、召回、阅读和审核。
3. **离线测试与效果评测各管一层**：前者证明代码行为，后者观察模型研究效果，不能互相代替。
4. **可观察性要从早期建立**：否则“没搜索”“没写报告”可能只是日志或页面没有展示。
5. **先诊断再付费扩展**：回放、逐题分析和复用能节省成本；反复盲重跑会增加费用而不增加解释力。
6. **冻结是选择，不是胜利声明**：最新补丁、最高单次成绩与最终交付选择是不同概念。
7. **人机协作需要真实验证**：自然语言适合描述目标和异常，原始输出、测试和版本记录负责约束实现。
