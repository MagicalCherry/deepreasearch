## 共享工作状态

ResearchState是各角色共享的工作本，ResearchPhase是研究所处阶段。create_initial_state初始化iteration=0、max_iterations=3；run_sync会再以图实例的max_iterations覆盖该值。

| 数据类别 | 状态字段 |
|---|---|
| 原始任务与进度 | query、session_id、phase、iteration、max_iterations |
| 规划 | outline、research_questions、key_entities、hypotheses、knowledge_graph等 |
| 资料 | facts、data_points、raw_sources |
| 写作 | draft_sections、final_report、references |
| 审核 | critic_feedback、unresolved_issues、quality_score、pending_search_queries |

学员原话：

> Scout搜索到的事实应该写入   facts， data_points，raw_sources；writer写draft_sections、final_report、references；最后critic写critic_feedback、 unresolved_issues、quality_score、pending_search_queries

核对：上述分类符合状态的用途，但字段存在不代表实际被某个角色写入。侦探源码可见facts和data_points写入，未找到raw_sources引用；writer与critic列出的主要写入字段均有代码对应。详细角色表将在逐文件阅读后补全。

## 架构师阅读笔记

PLANNING_PROMPT以query填入研究课题，要求模型输出JSON，包含研究假设、六组章节标题/描述/检索词，以及核心问题。六组章节为市场概况、竞争格局、技术趋势、政策环境、挑战机遇、未来展望。

_convert_flat_to_outline把sec_N_title、sec_N_desc、sec_N_query整理成章节对象，把questions按分号拆成research_questions；初始规划再为章节补id、status=pending、priority、search_queries等字段。

| 角色 | 读取的主要状态 | 写回的主要状态 |
|---|---|---|
| architect（初始规划） | query、phase | outline、research_questions、hypotheses、key_entities、mind_map、knowledge_graph、phase；消息与错误记录 |

该角色有调整大纲方法，但当前run_sync只在开头调用一次architect，审核回路里不会再次调用它。此处记录调用事实，不代替学员填写问题预判。

学员对架构师的复述原文：

> 这个大纲，一方面写假设驱动研究中的假设，另一个方面是给出大致的文章写法和方向，让其给出输出报告的整体结构。每一个章节都要根据query和假设给出对应的搜索关键词。

代码补充：章节搜索词和假设均由同次规划输出，但代码没有逐条强制校验每个章节检索式与某个假设的对应关系；Scout分析搜索结果时会收到研究问题、章节信息和假设。

## 侦探阅读笔记

| 方法 | 实际行为 |
|---|---|
| process | 取pending章节中的前三个，用asyncio.gather并行研究；此处不是自动分批研究所有章节 |
| _research_section | 逐个执行章节search_queries，合并结果后分析；写事实、数据点、洞察、实体和假设证据 |
| _analyze_search_results | 最多取15条结果，每条含标题、URL、来源、日期，以及summary前300字符；同时提供研究问题、章节标题/描述和假设 |
| _execute_deep_search | 跟进source_tracing_queries与follow_up_queries，各先取前2条，默认depth=1、max_depth=2；更深追踪使用further_tracing_queries前2条 |
| _analyze_deep_search_results | 最多取6条结果，每条只给标题、来源和summary前300字符，再分析事实和追踪线索 |
| deep_read_url | 定义了抓网页正文并分析的方法，但在给定deep_research_v2的Python源码中搜索只找到定义，没有找到调用点 |

这里的300是Python字符串切片的字符数，不是token数。“深度搜索”是增加检索与追踪；不能据此认定已经阅读网页全文。

侦探主要读取query、outline、hypotheses、phase、iteration/max_iterations及搜索模式；主要更新facts、data_points、insights、knowledge_graph、hypotheses、章节状态，补搜时也清空pending_search_queries并更新phase。原项目包含可选Milvus路径，本阶段仅阅读，不启用向量检索。

学员对摘要与正文的复述原文：

> 不能提取摘要没有的答案，要进行阅读全文进一步的搜索

核对：摘要没有提供的答案，不能仅凭摘要可靠提取并作为已核实事实；应获取正文核对，必要时继续检索。继续搜索与阅读正文是不同动作，当前源码未找到deep_read_url的调用点。

## 笔杆阅读笔记

| 方法 | 输入与处理 | 写回 |
|---|---|---|
| process | WRITING进入写作，REVISING进入修订 | 对应方法更新状态 |
| _write_section | 研究问题、章节信息、相关facts（没有时取前10条facts）、前10条数据点、前5条洞察及相关图表；要求生成Markdown正文与引用 | draft_sections、章节status=drafted、references |
| _synthesize_report | 按大纲顺序整合章节草稿，汇集引用和事实来源（来源列表最多30条）；生成摘要、正文、结论及参考文献 | final_report、references；写作完成后phase=REVIEWING |
| _revise_report | 原报告前6000字符、未解决反馈、最近5条事实（每条前200字符） | 用revised_content替换final_report；按返回的问题ID标记反馈已解决；phase=REVIEWING |

Writer依赖共享状态中的素材，不自行搜索或抓取网页正文。章节提示词要求观点有事实或数据支撑、使用可点击引用；这是模型写作要求，不能直接等同于程序已经验证引用。

学员对Writer的复述原文：

> writer会看scout搜索到的知识、尽量根据阅读全文后的内容去写报告，缺少关键证据他自己不可以去利用模型知识去补齐，必须有依据，所以只能交给后续critic指正并让scout重新搜索才行。

核对：这是期望的证据原则。实际Writer读取的是共享状态的事实等素材，并不保证这些事实来自全文阅读；缺证据后的补搜也依赖Critic识别问题并满足路由条件，不能保证自动发生。

## 评论家阅读笔记

REVIEW_PROMPT要求检查来源、逻辑、偏见、时效性和完整性，输出评分、结论、问题、补搜建议和事实核查判断。实际_review_content优先拼接draft_sections，仅在没有草稿时使用final_report；报告输入截取前8000字符，另附前20条事实（每条前150字符）、前15条数据点和大纲。

process将问题追加至critic_feedback，写quality_score、unresolved_issues（本轮critical/major问题数），并更新phase、iteration及需要补搜时的pending_search_queries。收到verdict=pass就完成；代码没有额外校验分数必须达到7，分数门槛出现在提示词中。

_analyze_issues_for_routing将missing_source、incomplete、outdated视为需搜索类型，只计critical/major；只有问题同时标注requires_new_search且有search_query才收集其关键词，另外加入missing_aspects前3项。返回补搜要求：有关键词、有上述搜索类问题或遗漏方面，且严重问题总数为0或搜索类严重问题占比大于30%；关键词去重后最多5条，否则转Writer修订。两条回路仍受run_sync最多3轮约束。
